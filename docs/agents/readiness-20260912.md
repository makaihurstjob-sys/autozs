## Defects and limits requiring follow-up

1. **High: traffic stale alert can be suppressed by unrelated freshness.** Operational alerts.py `_ebay_traffic_alert_specs` uses a global maximum across traffic timestamps and every listing's views_measured_at, without account or listing-status scope. A fresh scrape for account A suppresses an alert for active account B with stale/missing reports. An ended listing can also suppress it. Fresh view counts do not establish current impressions. The four new tests exercise only a single account and no real traffic rows, so they do not cover these cases. Use per-account report freshness and separate metric availability/coverage rather than treating any new view as fresh impressions.

2. **High: row metadata can falsely refresh traffic evidence.** The alert includes max(EbayTrafficRecord.updated_at); ebay_traffic.py summary also takes max of last_updated_at and updated_at at approximately line 570. `EbayTrafficRecord` inherits `TimestampMixin` (domain.py lines 12 and 362), whose updated_at advances on any ORM update. The summary itself fills missing record.title and record.sku (ebay_traffic.py approximately lines 501-504), so a later flush of this metadata enrichment can renew apparent freshness without a new observation. Prefer explicit source observation/report completion evidence; do not use generic row updates as stronger evidence than a known stale last_updated_at. Regressions: stale source timestamp plus fresh updated_at still stale; missing title/sku enrichment and flush must not renew freshness; fresh views with stale impressions must not imply both fresh; one fresh account must not mask another active stale account; ended-listing views must not mask active listings; recovery resolves only the affected account alert.

3. **Medium: replacement numeric checks remain weaker than restock.** At e852753 orders.py `_queue_replacement_publish` rejects missing price but not zero, negative or nonfinite price, and rejects negative shipping but not nonfinite shipping. With otherwise fresh observations a directly persisted invalid row passes this gate and creates a job. The rotation SQL in listing_jobs.py accepts positive infinity for price and shipping; later readiness/package checks still run, so SQL admission alone does not prove end-to-end publication. The importer fix clears corresponding observations for invalid values and bulk overwrites, closing the reviewed ordinary ingestion routes, and null legacy observations block legacy rows. That makes normal-path exposure smaller; it does not make these final queue gates independently safe. Apply the finite positive-price/nonnegative-shipping rule at both gates and add regressions with fresh timestamps plus zero/negative/infinite price and infinite shipping. Include a positive free-shipping control. SQLite converts NaN to NULL in some paths, so test in-memory gate behavior separately from database persistence. Existing publish tests mock rotation readiness/package; preserve real downstream tests as well.

4. **Traffic alerts are detection, not prevention or repair.** They neither restart Chrome nor guarantee report acquisition. Stuck-run detection uses updated_at, so non-progress updates can postpone its two-hour threshold. Push requires the existing configured dispatcher, subscriptions and permission; adding a default toggle is not delivery evidence. Do not state stale data is impossible after deployment.

5. **Capture and final-action limits persist.** Explicit observation fields preserve received evidence but cannot validate permissive stock detectors. Publish/rotation freshness checks run at queue creation, not a universal final browser-submit authorization boundary. A delayed publish can outlive its evidence. Scope a follow-up if claiming final-action freshness; the restock bulk-upload path already has separate execution guards.
